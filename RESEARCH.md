# Landscape Research: Secure VMs + SDKs for AI Agents

> Deep research conducted 2026-08-31 across four parallel tracks. Every factual claim carries an inline source link. Gap analysis and product direction live in [SCOPE.md](SCOPE.md).

## TL;DR

**Who's working on this?** Everyone — the space split into four camps between 2024 and 2026:

1. **Sandbox startups/SDKs** — E2B (Firecracker, 94% of Fortune 100 signed up), Daytona ($24M Series A, went closed-source June 2026), Modal (gVisor + GPUs, ~$1.1B+), Northflank (BYOC/Kata), Blaxel (perpetual sandboxes, OpenAI Tier-1), Runloop, Scrapybara, Fly.io Sprites, Cloudflare Sandbox SDK, Vercel Sandbox, Together Code Sandbox.
2. **Isolation primitives** — AWS Firecracker (dominant), Google gVisor (Anthropic, OpenAI, Modal all use it), Kata Containers, Cloud Hypervisor, Microsoft Hyperlight (~1ms microVMs), Wasmtime/WASI, and OS-level mechanisms (seccomp/Landlock/Seatbelt) that power Claude Code and Codex locally.
3. **Big clouds + AI labs** — AWS Bedrock AgentCore (Firecracker per session + Cedar policy engine), Azure dynamic sessions + Entra Agent ID, Google's gVisor-everywhere strategy + SPIFFE agent identity, Anthropic sandbox-runtime, OpenAI Codex sandboxing, Docker Sandboxes, NVIDIA NeMo Guardrails.
4. **Open source** — microsandbox (libkrun, local-first), Alibaba OpenSandbox (~15k stars in 9 months), kubernetes-sigs/agent-sandbox, Anthropic srt, Dormice, plus a graveyard (Arrakis abandoned, Daytona closed-sourced).

**The shared industry thesis:** model-layer defenses against prompt injection are probabilistic, so hard guarantees must come from the *environment* — isolation, egress control, credential brokering, policy, and audit. The unclaimed territory is the **governance layer** (policy-as-code + tamper-evident audit that works across runtimes) — see [SCOPE.md](SCOPE.md).

## Part 1 — Sandbox Startups & SDK Platforms

The "give every agent a computer" category has consolidated into three layers: raw isolation primitives (Firecracker, gVisor, Kata, libkrun), embeddable sandbox runtimes with agent-first SDKs, and managed platforms with BYOC/GPU options ([amux sandboxing guide](https://amux.io/guides/ai-agent-sandboxing/), [Manveer's sandboxing guide](https://manveerc.substack.com/p/ai-agent-sandboxing-guide)). A signal of category maturity: in April 2026 OpenAI's Agents SDK shipped hosted sandbox clients for seven providers including E2B and Blaxel ([Ry Walker Research — E2B](https://rywalker.com/research/e2b), [Ry Walker Research — Blaxel](https://rywalker.com/research/blaxel)).

### Player Profiles

### E2B
- Open-source sandbox runtime + hosted cloud purpose-built for AI agents; over 1B sandboxes started, 3.5M+ monthly SDK downloads, and 94% of Fortune 100 signed up as of mid-2026 ([Ry Walker Research](https://rywalker.com/research/e2b), [checkthat.ai](https://checkthat.ai/brands/e2b)).
- Firecracker microVM isolation — the same tech behind AWS Lambda — with median sandbox creation down to ~78ms p50 by January 2026 ([amux guide](https://amux.io/guides/ai-agent-sandboxing/), [Ry Walker Research](https://rywalker.com/research/e2b)).
- Python and JS/TS SDKs around a sandbox-lifecycle API (create, exec, filesystem, expose ports); Hobby free tier with $100 credit and 1h sessions, Pro at $150/mo with 24h sessions and up to 1,100 concurrent sandboxes ([E2B pricing](https://e2b.dev/pricing)).
- $21M Series A led by Insight Partners (July 2025), following an $11.5M seed; customers include Perplexity, Hugging Face, and Groq ([VentureBeat](https://venturebeat.com/ai/how-e2b-became-essential-to-88-of-fortune-100-companies-and-raised-21-million), [E2B blog](https://e2b.dev/blog/series-a)).
- Enterprise: BYOC into your own AWS VPC (GCP/Azure planned), on-prem/self-hosting, RBAC, US/EU data residency for EU AI Act compliance, uptime SLAs — but no publicly confirmed SOC 2 certification ([E2B Enterprise](https://e2b.dev/enterprise), [Blaxel SOC 2 roundup](https://blaxel.ai/blog/soc-2-compliant-sandbox-providers)).
- Weakness cited by competitors: 24-hour max session length vs. unlimited-duration rivals ([Northflank comparison](https://northflank.com/blog/best-code-execution-sandbox-for-ai-agents)).

### Daytona
- Pivoted from dev-environment tooling to AI sandbox infrastructure (Dec 2024–Feb 2025); "give every agent a computer" positioning; hit $1M forward run rate in under 3 months, doubling six weeks later ([Unicorner](https://read.unicorner.news/p/daytona), [PR Newswire](https://www.prnewswire.com/news-releases/daytona-raises-24m-series-a-to-give-every-agent-a-computer-302680740.html)).
- $24M Series A led by FirstMark (Feb 2026) with Pace Capital, Upfront, plus strategic checks from Datadog and Figma Ventures ([TechNews180](https://technews180.com/funding-news/firstmark-leads-24m-round-in-agent-infrastructure-startup-daytona/)).
- Four sandbox classes — Container, Linux VM, Windows, GPU; OCI containers by default with optional Kata Containers hardware isolation, configurable network egress controls, and sub-90ms (as low as 27ms pre-warmed) starts ([Modal's comparison](https://modal.com/resources/best-code-execution-sandboxes-ai-agents), [AgentMarketCap](https://agentmarketcap.ai/blog/2026/04/07/ai-agent-sandbox-infrastructure-e2b-modal-daytona-fly-machines-secure-code-execution)).
- Compliance-first pitch: SOC 2 Type I achieved (Type II underway), HIPAA and GDPR claimed out of the box; notable caveat — moved away from fully open-source in June 2026 ([Blaxel SOC 2 roundup](https://blaxel.ai/blog/soc-2-compliant-sandbox-providers)).

### Modal (Sandboxes)
- Serverless AI infrastructure company whose Sandboxes primitive runs untrusted agent code with gVisor isolation next to on-demand GPUs; scales to 20k+ concurrent containers (built for 100k+ concurrent sandboxes) with sub-second cold starts ([Northflank comparison](https://northflank.com/blog/best-code-execution-sandbox-for-ai-agents), [Sacra](https://sacra.com/c/modal-labs/)).
- Python-first developer experience; JavaScript/TypeScript and Go SDKs (beta) can create sandboxes and call deployed functions, though function definitions remain Python-only ([Modal blog](https://modal.com/blog/sdk-javascript-go)).
- $87M Series B led by Lux Capital at $1.1B post-money (Sep 2025); by May 2026 reportedly in talks for $150–250M at ~$4.5B ([Modal blog](https://modal.com/blog/announcing-our-series-b), [Sacra](https://sacra.com/c/modal-labs/)).
- Enterprise: SOC 2 Type II completed and HIPAA-compliant workloads supported via BAA on Enterprise plans ([Modal HIPAA announcement](https://modal.com/blog/hipaa)).

### Northflank
- Production workload platform (apps, DBs, jobs, GPUs) that added multi-tenant AI sandboxes; differentiates on choice of isolation — Kata Containers, Firecracker, or gVisor — any OCI image, and unlimited session duration ([Northflank platform ranking](https://northflank.com/blog/top-ai-sandbox-platforms-for-code-execution)).
- Only vendor in its class with self-serve BYOC and public BYOC pricing: deploy the control plane into AWS, GCP, Azure, Oracle, CoreWeave, Civo, bare-metal, or on-prem ([Northflank BYOC comparison](https://northflank.com/blog/best-byoc-sandbox-platforms)).
- Cheapest published PaaS compute in the category: $0.01667/vCPU-hr billed per second; a 200-sandbox fleet costs ~$2,060 on BYOC vs $7,200 on PaaS ([Northflank pricing comparison](https://northflank.com/blog/ai-sandbox-pricing)).
- Enterprise: SOC 2 Type II, HIPAA with BAA, OIDC/SAML SSO, audit logging ([Blaxel SOC 2 roundup](https://blaxel.ai/blog/soc-2-compliant-sandbox-providers)).

### Blaxel
- YC-backed (Spring 2025) "cloud for the AI agent economy"; $7.3M seed led by First Round ([Blaxel blog](https://blaxel.ai/blog/Blaxel-Raises-7-3M-Seed-Round-led-by-First-Round-to-Build-Cloud-Infrastructure-for-the-AI-Agent-Eco-23247e47b1ea8067b923d998364e3ced)).
- Signature feature is "perpetual" sandboxes: microVMs boot in milliseconds, auto-suspend after ~1 second of idle, resume in <25ms, and persist state indefinitely with zero compute cost on standby ([Blaxel cloud sandboxes post](https://blaxel.ai/blog/best-cloud-sandboxes-ai-agents-2026), [Ry Walker Research](https://rywalker.com/research/blaxel)).
- Named a Tier-1 sandbox provider in OpenAI's Agents SDK (April 2026) — a significant distribution channel ([Ry Walker Research](https://rywalker.com/research/blaxel)).
- Enterprise: SOC 2 Type II, ISO 27001, HIPAA via BAA, included audit logs, managed networking/egress gateways; no BYOC ([Blaxel SOC 2 roundup](https://blaxel.ai/blog/soc-2-compliant-sandbox-providers)).

### Runloop
- SF startup selling "devboxes" — isolated, stateful cloud dev environments for AI coding agents — plus a differentiated eval layer (public Benchmarks like SWE-bench, custom Scenarios and scorers) ([Runloop press](https://runloop.ai/media/runloop-raises-7m-seed-round-to-bring-enterprise-grade-infrastructure-to-ai-coding-agents), [Runloop benchmarks](https://runloop.ai/benchmarks)).
- Dual-layer isolation (microVM + container) on a custom bare-metal hypervisor; large images boot in under two seconds; supports 30,000+ concurrent environments ([Runloop enterprise sandboxes announcement](https://runloop.ai/media/runloop-unveils-enterprise-grade-sandboxes-for-ai-coding-agents)).
- Enterprise: SOC 2 Type II, HIPAA, GDPR with BAA/DPA; sells via AWS Marketplace ([Blaxel platform roundup](https://blaxel.ai/blog/ai-sandbox-platforms-secure-code-execution)).

### Scrapybara
- YC F24 company providing instant virtual desktop instances (Ubuntu, Windows, browser) for computer-use agents — the "computer" rather than just the code interpreter ([YC launch](https://www.ycombinator.com/launches/MHN-scrapybara-a-computer-for-your-ai)).
- Unified API/SDKs in Python and TypeScript with low-level controls (bash, filesystem, browser) and an MCP server; integrates with computer-use models like OpenAI CUA and Claude ([The AI Report](https://www.theaireport.ai/tools/agents/scrapybara)).
- Modest disclosed funding (~$500K via Y Combinator) — much smaller war chest than infra rivals ([Crunchbase](https://www.crunchbase.com/organization/scrapybara)).

### Fly.io (Fly Machines + Sprites)
- Fly Machines are API-driven, hardware-isolated Firecracker/KVM VMs that boot any OCI image — long used as a DIY agent sandbox substrate ([Northflank agent runtime roundup](https://northflank.com/blog/top-ai-agent-runtime-tools)).
- In January 2026 Fly launched Sprites.dev: persistent Firecracker microVMs with 100GB NVMe where installed packages and files survive across sessions — explicitly aimed at coding agents and untrusted-code APIs ([Simon Willison](https://simonwillison.net/2026/Jan/9/sprites-dev/), [SDxCentral](https://www.sdxcentral.com/news/flyio-debuts-sprites-persistent-vms-that-let-ai-agents-keep-their-state/)).
- Sprites auto-idle to stop compute billing while preserving state; the company has publicly repositioned itself around agent-driven workloads ([Fly blog](https://fly.io/blog/kurt-scott-money-sprites/)).

### Cloudflare (Sandbox SDK)
- Open-source TypeScript Sandbox SDK for running untrusted code in isolated containers from Workers apps: command exec, file ops, background processes, PTY terminals, service preview URLs, and persistent code interpreters ([GitHub](https://github.com/cloudflare/sandbox-sdk), [Cloudflare docs](https://developers.cloudflare.com/sandbox/)).
- Built on Cloudflare Containers at the edge; container-based isolation rather than hardware-virtualized microVMs — a deliberate contrast with Firecracker-based rivals ([InfoQ GA coverage](https://www.infoq.com/news/2026/04/cloudflare-sandboxes-ga/)).
- GA April 2026 on the Workers Paid plan with active-CPU pricing; GA added backup/restore snapshots and credential injection via outbound Workers (egress mediation) ([Cloudflare changelog](https://developers.cloudflare.com/changelog/post/2026-04-13-containers-sandbox-ga/), [InfoQ](https://www.infoq.com/news/2026/04/cloudflare-sandboxes-ga/)).
- First-class integrations: a Cloudflare backend ships inside the OpenAI Agents SDK ([Cloudflare tutorial](https://developers.cloudflare.com/sandbox/tutorials/openai-agents/)).

### Vercel Sandbox
- Ephemeral Firecracker microVMs on Vercel's Fluid compute / internal "Hive" platform for untrusted and AI-generated code; GA January 30, 2026 ([Vercel GA blog](https://vercel.com/blog/vercel-sandbox-is-now-generally-available)).
- Open-source Node/TypeScript SDK (`@vercel/sandbox`) and CLI; full sudo and package managers; snapshots restore complex environments instantly ([Vercel GA blog](https://vercel.com/blog/vercel-sandbox-is-now-generally-available)).
- Ran a $1 million public hacker challenge against its sandbox isolation — an unusually aggressive security-confidence signal ([Vercel blog](https://vercel.com/blog/one-million-dollar-hacker-challenge-for-vercel-sandbox)).
- Production users include Roo Code and Blackbox AI ([Vercel GA blog](https://vercel.com/blog/vercel-sandbox-is-now-generally-available)).

### Together AI (Together Code Sandbox)
- Together AI acquired CodeSandbox (Dec 2024) to add a code-interpreter/sandbox layer to its AI Acceleration Cloud; SDK GA May 2025, rebranded Together Code Sandbox ([SiliconANGLE](https://siliconangle.com/2024/12/12/together-ai-acquires-codesandbox-adds-code-interpreter-ai-development-platform/), [CodeSandbox blog](https://codesandbox.io/blog/joining-together-ai-introducing-codesandbox-sdk)).
- Proprietary Firecracker implementation with memory snapshot/restore and copy-on-write live VM cloning: 500ms resume from snapshot, 2.7s P95 cold create ([Together blog](https://www.together.ai/blog/code-sandbox)).
- Rich dev-environment features beyond bare exec: Dev Containers, port previews, git-versioned persistent storage, multi-user collaborative sessions, hot-swappable VM sizing ([Together blog](https://www.together.ai/blog/code-sandbox)).

### Other Notable Players
- **Morph Cloud** — "Infinibranch" runtime that snapshots, branches, and restores entire VM states in under 250ms for parallelized agent runs and RL environments; seed backing led by Khosla Ventures ([Morph Infinibranch](https://www.morph.so/blog/infinibranch/)).
- **Beam** — open-source, self-hostable E2B alternative with Docker-based sandboxing, GPU support, Python and Node SDKs, and no session time limits ([Beam blog](https://www.beam.cloud/blog/best-e2b-alternatives)).

### Cross-Cutting Observations
- **Isolation is the marketing battleground**: Firecracker microVMs dominate (E2B, Vercel, Together, Fly, Runloop, AWS), gVisor anchors Modal, Kata/choice-of-runtime anchors Northflank and Daytona, while Cloudflare bets on edge containers ([amux guide](https://amux.io/guides/ai-agent-sandboxing/)).
- **Pricing has converged on per-second compute + memory metering**, with the real differentiation in idle economics: suspend/resume with zero-compute standby (Blaxel, Fly Sprites, E2B pause, Together snapshots) vs. pure ephemerality (Vercel) ([Northflank pricing comparison](https://northflank.com/blog/ai-sandbox-pricing)).
- **Enterprise checklists are becoming table stakes**: SOC 2 Type II confirmed at Modal, Northflank, Blaxel, Runloop, and Fly.io; BYOC/VPC deployment is the sharpest enterprise wedge ([Blaxel SOC 2 roundup](https://blaxel.ai/blog/soc-2-compliant-sandbox-providers), [Northflank BYOC comparison](https://northflank.com/blog/best-byoc-sandbox-platforms)).
- **Distribution via agent frameworks matters**: OpenAI Agents SDK's hosted sandbox clients (seven providers) suggest sandboxes are becoming a pluggable commodity layer selected by framework default ([Ry Walker Research](https://rywalker.com/research/e2b)).

## Part 2 — Isolation Primitives

### Tradeoff Comparison

| Technology | Cold start / boot | Memory overhead | Isolation strength | GPU support | Notable users (AI sandbox in **bold**) |

### Where Plain Containers Fall Short

Containers isolate with namespaces and cgroups but [share the host kernel, so a single kernel flaw exposes every workload on the machine](https://www.wiz.io/academy/container-security/container-escape). This is not theoretical: [Dirty Pipe (CVE-2022-0847) let an unprivileged container process write to read-only host-mounted files and escape](https://securitylabs.datadoghq.com/articles/dirty-pipe-container-escape-poc/), [CVE-2019-5736 (runc), CVE-2022-0847, and CVE-2022-1015 each demonstrated that containers sharing a Linux kernel cannot be isolated by Linux itself](https://www.systemshardening.com/articles/cross-cutting/gvisor-kata-shared-kernel-defense/), and [three new runc escapes (CVE-2025-31133, CVE-2025-52565, CVE-2025-52881) landed as recently as late 2025](https://www.sysdig.com/blog/runc-container-escape-vulnerabilities). A standard container exposes [400+ host syscalls to the workload](https://northflank.com/blog/what-is-gvisor). AI agents are a worst-case tenant because [they generate and execute unreviewed code at runtime from potentially malicious inputs](https://blaxel.ai/blog/container-escape), which is why every serious agent platform layers a microVM, user-space kernel, or Wasm boundary on top — or replaces containers entirely.

### AWS Firecracker

Firecracker is a minimal Rust VMM on KVM that boots a real Linux guest kernel with only five virtio devices (no PCI, no BIOS, no USB), wrapping each workload in a hardware virtualization boundary; a companion "jailer" adds seccomp/cgroup/namespace confinement around the VMM process itself. Its published spec commits to [≤125 ms from API call to guest init and ≤5 MiB VMM memory overhead per microVM](https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md), with [creation rates up to 150 microVMs per second per host](https://firecracker-microvm.github.io/).

- **Security model**: the guest gets its own kernel; a guest kernel exploit still faces the tiny VMM and KVM. [The minimal device set is a deliberate attack-surface decision — every unimplemented feature is attack surface that doesn't exist](https://e2b.dev/blog/firecracker-vs-qemu).
- **Maturity / users**: powers [AWS Lambda and Fargate](https://www.pandastack.ai/blog/firecracker-use-cases/); among AI sandboxes, [E2B (millions of sandboxes weekly), Vercel Sandbox (Notion, Blackbox AI as customers), and Fly.io Sprites all run on Firecracker](https://blaxel.ai/blog/vercel-sandbox-alternatives), and [AWS Bedrock AgentCore provisions a dedicated Firecracker microVM per agent session](https://www.akshayparkhi.net/2026/Mar/11/how-firecracker-microvms-power-agentcore-runtime-from-125ms-boot/).
- **Limitations**: [no GPU or PCI passthrough — platforms built on it are CPU-only by design](https://northflank.com/blog/gpu-sandboxes) ([longstanding open issue](https://github.com/firecracker-microvm/firecracker/issues/849)); requires direct KVM access, meaning [bare-metal hosts or nested virtualization, which adds latency and blocks PCIe passthrough](https://www.spheron.network/blog/ai-agent-code-execution-sandbox-e2b-daytona-firecracker/). Notably, [AWS began offering nested virtualization on virtualized EC2 (C8i/M8i/R8i) in February 2026](https://www.infoq.com/news/2026/03/aws-ec2-nested-virtualization/), easing the bare-metal requirement.

### Google gVisor

gVisor interposes a user-space "application kernel" (the Sentry, ~200 KLOC of Go) between the workload and the host: [container syscalls are intercepted and reimplemented in user space, so the application never talks to the host kernel directly](https://northflank.com/blog/what-is-gvisor), with filesystem access mediated by a separate Gofer process. [The default interception platform since 2023 is Systrap (seccomp-trap based), replacing slower ptrace](https://gvisor.dev/blog/2023/04/28/systrap-release/); a KVM platform uses hardware virtualization for faster context switches.

- **Security model**: [the design goal is minimizing the System API attack vector — the Sentry's own seccomp policy allows only ~50 host syscalls versus 400+ for a bare container](https://northflank.com/blog/what-is-gvisor), and [defense-in-depth means an attacker must compromise both the Sentry and the reduced host interface](https://gvisor.dev/docs/architecture_guide/security/).
- **Performance**: [no penalty for CPU-bound or memory-access work; overhead is proportional to syscall frequency, concentrated in structured syscall and VFS costs](https://gvisor.dev/docs/architecture_guide/performance/) — [roughly 10–30% on syscall/I/O-heavy workloads](https://securemachinery.com/2026/07/04/kata-containers-vs-gvisor-security-architecture-performance-full/).
- **Maturity / users**: [Google runs millions of gVisor instances daily (GKE Sandbox, App Engine Standard, Cloud Run); Anthropic uses it to contain code execution within claude.ai; OpenAI for higher-risk code execution; Modal for its sandboxes; Cloudflare for Pages builds; DigitalOcean App Platform; Northflank and Beam for sandboxed GPU workloads](https://gvisor.dev/users/).
- **Limitations**: syscall compatibility is a large-but-incomplete Linux subset; syscall-dense workloads pay real overhead; it is [a weaker boundary than a hardware VM — the Sentry still runs on the host kernel](https://amux.io/guides/ai-agent-sandboxing/). GPU support (nvproxy) is a curated CUDA surface rather than full device passthrough, yet is production-proven for [GPU/serverless AI sandboxes](https://gvisor.dev/users/).

### Kata Containers

Kata is an OCI-compatible runtime that [boots a lightweight hardware VM per Kubernetes pod — all containers in the pod share one guest kernel — so standard container tooling gains VM isolation transparently](https://stackharbor.com/en/knowledge-base/kata-containers-runtime/). It supports pluggable VMMs: QEMU, Cloud Hypervisor, and Firecracker.

- **Numbers**: [boot time ~150–300 ms depending on VMM and configuration, with ~100–200 MiB per pod for guest kernel and agent](https://stackharbor.com/en/knowledge-base/kata-containers-runtime/).
- **Security model**: full hardware virtualization boundary per pod; the tradeoff versus Firecracker-native platforms is a larger stack (runtime, agent, guest OS) in exchange for Kubernetes/OCI compatibility.
- **Maturity / users**: [Alibaba and Ant Group run probably the largest production deployment, with thousands of tasks on Kata; Baidu uses it for function compute and cloud container instances at massive scale](https://katacontainers.io/use-cases/). [Northflank pairs Kata with Cloud Hypervisor for isolated workloads at scale](https://northflank.com/blog/guide-to-cloud-hypervisor). It underpins [Confidential Containers (TEE-based isolation), which became a CNCF incubating project in July 2026 with backing from Azure, Intel, AMD, IBM, NVIDIA, Alibaba, and Red Hat](https://www.cncf.io/blog/2026/07/22/confidential-containers-becomes-a-cncf-incubating-project/).
- **GPU**: the standout capability — [VFIO passthrough of GPUs, FPGAs, and SR-IOV NICs with QEMU](https://stackharbor.com/en/knowledge-base/kata-containers-runtime/); [NVIDIA's reference stack supports cold-plug GPU passthrough, attaching the GPU at VM launch](https://github.com/kata-containers/kata-containers/blob/main/docs/use-cases/NVIDIA-GPU-passthrough-and-Kata-QEMU.md), integrated with the [NVIDIA GPU Operator](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/deploy-kata-containers.html). Requires KVM, so the same bare-metal/nested-virt constraint applies.

### Cloud Hypervisor

A Rust VMM built on the [rust-vmm](https://github.com/cloud-hypervisor/cloud-hypervisor) crates that runs on both KVM and Microsoft Hypervisor (MSHV), positioned between Firecracker's minimalism and QEMU's generality: virtio-only device model plus CPU/memory/device hotplug, vhost-user offload, live migration, and Windows and Linux guests.

- **Numbers**: [boot to userspace in under 100 ms, ~200 ms to a fully running VM](https://northflank.com/blog/guide-to-cloud-hypervisor).
- **Security model**: memory-safe Rust implementation with a [minimal, compact footprint and a strong focus on security](https://github.com/cloud-hypervisor/cloud-hypervisor); hardware VM boundary identical in kind to Firecracker's, with more device surface in exchange for capability.
- **Maturity / users**: [started at Intel, now Linux Foundation-hosted and supported by Alibaba, AMD, Ampere, Arm, ByteDance, Intel, Microsoft, SAP, and Tencent Cloud](https://www.cloudhypervisor.org/); [Northflank uses it as the primary VMM under Kata in production](https://northflank.com/blog/firecracker-vs-cloud-hypervisor).
- **GPU / limitations**: supports [VFIO device passthrough (GPUs included) and live migration while keeping a small auditable codebase](https://northflank.com/blog/what-are-kata-containers) — the common choice when teams want "Firecracker-style microVMs but with GPUs." Requires KVM/MSHV, so bare metal or nested virtualization again.

### QEMU microvm

A stripped QEMU machine type [inspired by Firecracker and NEMU: virtio-mmio devices only, with PCI, ACPI, and most emulated hardware removed, explicitly targeting fast boot, minimal attack surface (measured in exposed IO ports/MMIO regions), and short-lived guests](https://www.qemu.org/docs/master/system/i386/microvm.html).

- **Numbers**: [sub-300 ms to a fully networked guest with an agent; a stripped configuration boots Linux in under 90 ms](https://blog.bott.im/micro-vms-with-qemu-millisecond-boots-smaller-attack-surface/).
- **Security model / maturity**: KVM hardware isolation with a much smaller QEMU device surface than the default `q35` machine, but still the QEMU codebase — larger TCB than purpose-built Rust VMMs. Documented and shipped by [Ubuntu](https://ubuntu.com/server/docs/explanation/virtualisation/qemu-microvm/) and usable anywhere QEMU runs; it is the pragmatic option when you already operate QEMU.
- **Limitations**: [virtio-mmio only — no PCI means no GPU passthrough in this mode](https://www.qemu.org/docs/master/system/i386/microvm.html) (full QEMU with VFIO is the escape hatch, at the cost of the enlarged attack surface Firecracker was created to avoid).

### Microsoft Hyperlight and Hyperlight-Wasm

Hyperlight is [an embeddable Rust VMM that creates hypervisor-isolated micro-VMs around individual functions with no guest kernel, no OS, and no virtual devices — guests are purpose-built against the Hyperlight guest library](https://github.com/hyperlight-dev/hyperlight) and get only a slab of memory and a vCPU. Hyperlight-Wasm puts [a no_std build of Wasmtime inside the micro-VM so standard Wasm components (Rust, JS, Python, C, Go) run behind two layers: the Wasm sandbox and the hypervisor wall](https://opensource.microsoft.com/blog/2025/03/26/hyperlight-wasm-fast-secure-and-os-free/).

- **Numbers**: [~1–2 ms to spin up a micro-VM, with warm execution around 0.0009 s (0.9 ms) and sub-millisecond as the target](https://opensource.microsoft.com/blog/2025/02/11/hyperlight-creating-a-0-0009-second-micro-vm-execution-time/) — versus [~125 ms at the low end of traditional VM startup](https://opensource.microsoft.com/blog/2024/11/07/introducing-hyperlight-virtual-machine-based-security-for-functions-at-scale/).
- **Security model**: hardware virtualization (KVM, Microsoft Hypervisor, or WHP on Windows) with essentially no device attack surface because there are no devices; [a Wasm escape still lands inside a hardware-enforced box](https://developers.slashdot.org/story/25/03/30/0627205/microsoft-announces-hyperlight-wasm-speedy-vm-based-security-at-scale-with-a-webassembly-runtime).
- **Maturity / users**: [CNCF Sandbox project since February 2025](https://opensource.microsoft.com/blog/2025/03/26/hyperlight-wasm-fast-secure-and-os-free/); [powers Azure Front Door's Edge Actions service](https://thenewstack.io/hyperlight-wasm-azure-goes-the-final-wasi-mile/). Younger and less battle-tested than Firecracker or gVisor.
- **Limitations**: cannot run unmodified Linux binaries — no kernel means no syscalls, so workloads must target the guest library or compile to Wasm; no GPU; the guest programming model is the whole constraint.

### WebAssembly Sandboxes (Wasmtime, WasmEdge)

Wasm runtimes execute code against a virtual instruction set inside a linear-memory sandbox: [there is no syscall invocation path at all — host capabilities (files, sockets, clocks) exist only if explicitly injected through WASI's capability-based interfaces at instantiation time](https://dev.to/guyoung/boxagnts-tool-system-2-the-security-model-of-wasmtime-sandboxing-1cj0).

- **Numbers**: [instances start in microseconds and use megabytes](https://cosmonic.com/blog/ai-sandbox-guide/) — orders of magnitude below even Firecracker.
- **Security model**: software fault isolation plus deny-by-default capabilities; [NVIDIA's research on sandboxing agentic workflows specifically recommends Wasm for executing LLM-generated code as a natural fit for least-privilege agents](https://cosmonic.com/blog/ai-sandbox-guide/). Weaker than hardware virt against runtime-compiler bugs, which is exactly the gap Hyperlight-Wasm closes.
- **Maturity / users**: [Wasmtime hit 1.0 in 2022 with Fastly Compute and Shopify (which saw ~50% faster execution after switching) in production, under the Bytecode Alliance (Fastly, Intel, Mozilla, Microsoft, Google, Arm, Shopify)](https://bytecodealliance.org/articles/wasmtime-1-0-fast-safe-and-production-ready); [Wasmtime leads on standards (WASI 0.2, Component Model), while CNCF-hosted WasmEdge targets cloud-native/edge and ships AI-inference (WASI-NN) extensions](https://reintech.io/blog/wasmtime-vs-wasmer-vs-wasmedge-wasm-runtime-comparison-2026).
- **Limitations**: the compatibility wall is the story — [WASI has no fork/exec, no signals, and limited IPC](https://www.emergentmind.com/topics/webassembly-wasi-sandbox); [instances are single-threaded, with threading worked around by replicating module instances](https://metatype.dev/blog/2024/08/26/python-on-webassembly); [Python/npm packages with native extensions don't automatically translate to Wasm/WASI](https://metatype.dev/blog/2024/08/26/python-on-webassembly), so "run arbitrary pip installs" agent workloads mostly can't live here yet. No general GPU access; [resource isolation (CPU, disk I/O, entropy) is also weaker than VM-level controls](https://www.emergentmind.com/topics/webassembly-wasi-sandbox).

### OS-Level Mechanisms: seccomp, Landlock, Namespaces, Seatbelt

These restrict what a process can do on a *shared* kernel — no VMM, no boot time, no memory tax — and have become the default for local coding-agent sandboxes where spinning up VMs per shell command is impractical.

- **Namespaces + cgroups** are [the building blocks of nearly every Linux sandbox](https://gist.github.com/wincent/2752d8d97727577050c043e4ff9e386e), giving each process its own view of mounts, PIDs, and network plus resource limits — isolation of *visibility*, not of the kernel.
- **seccomp-BPF** filters which syscalls a process may make; [Docker's default profile is an allowlist that disables ~44 of 300+ syscalls](https://docs.docker.com/engine/security/seccomp/), and it is [layered into most other Linux sandboxes](https://gist.github.com/wincent/2752d8d97727577050c043e4ff9e386e) including Chrome and gVisor's own Sentry confinement.
- **Landlock**, [merged in Linux 5.13, is an LSM letting unprivileged processes restrict their own filesystem and network access](https://www.phoronix.com/news/Linux-5.13-Landlock-Lands) — [access control on kernel objects rather than syscall filtering, complementing seccomp](https://docs.kernel.org/userspace-api/landlock.html); inspired by XNU Sandbox, Capsicum, and Pledge.
- **macOS Seatbelt** (`sandbox-exec` + SBPL policies) is [a TrustedBSD MAC policy module](https://hacktricks.wiki/en/macos-hardening/macos-security-and-privilege-escalation/macos-security-protections/macos-sandbox/index.html); Apple [marks it deprecated but ships no replacement for CLI-process sandboxing, so it remains the only documented mechanism for confining arbitrary processes outside the App Store](https://github.com/apple/containerization/issues/737).
- **Who uses this for AI agents**: [Anthropic's sandbox-runtime (behind Claude Code's sandboxed bash) uses bubblewrap + seccomp on Linux and Seatbelt on macOS, deleting the network namespace and forcing all traffic through host-side filtering proxies](https://github.com/anthropic-experimental/sandbox-runtime); [OpenAI's Codex CLI uses Seatbelt on macOS and Landlock + seccomp on Linux, and Gemini CLI uses Seatbelt directly](https://gist.github.com/wincent/2752d8d97727577050c043e4ff9e386e); [both major agent vendors chose OS primitives over containers for their first-party local sandboxes](https://medium.com/@Koukyosyumei/how-claude-code-and-codex-sandbox-untrusted-code-ba39b493046a).
- **Limitations**: the kernel remains shared, so a kernel LPE defeats the sandbox — this tier is defense-in-depth for semi-trusted local work, not a multi-tenant boundary; policies are hard to write correctly, and Seatbelt's deprecated status leaves macOS on uncertain footing.

## Part 3 — Big Cloud & AI Labs: Enterprise Agent Governance

The industry has converged on a shared thesis: model-layer defenses against prompt injection are probabilistic, so the hard guarantees must come from the *environment* — sandboxes, egress controls, credential isolation, and policy engines. Anthropic states this bluntly: "when the user is the one typing the instruction, there's nothing anomalous for a classifier to catch" — only egress controls and filesystem isolation stopped a red-team injection that Claude executed 24 of 25 times ([Anthropic, "How we contain Claude"](https://www.anthropic.com/engineering/how-we-contain-claude)). The threat framing most vendors now reference is Simon Willison's ["lethal trifecta"](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) — private data + untrusted content + external communication — which security vendors have operationalized as "blast radius reduction" for agent deployments ([Sophos](https://www.sophos.com/en-us/blog/inside-the-lethal-trifecta-blast-radius-reduction-in-ai-agent-deployments), [TechTarget](https://www.techtarget.com/searchsecurity/tip/The-agentic-AI-lethal-trifecta-What-CISOs-should-know)).

### AWS — Bedrock AgentCore

AgentCore went [GA in October 2025](https://aws.amazon.com/about-aws/whats-new/2025/10/amazon-bedrock-agentcore-available) and is AWS's most complete answer to the governance question — it decomposes "keep the agent contained" into Runtime, Code Interpreter, Browser, Gateway, Identity, Policy, and Observability primitives.

- **Runtime & Code Interpreter isolation.** Each user session runs in a dedicated Firecracker microVM with isolated CPU, memory, and filesystem, booting in under 125 ms, with sessions up to 8 hours ([deep dive](https://joudwawad.medium.com/aws-bedrock-agentcore-deep-dive-6822e4071774)). Code Interpreter is the managed agent sandbox for Python/JS/TS with S3 file access and CloudTrail audit logging ([research notes](https://rywalker.com/research/agentcore-code-interpreter)).
- **Network scoping.** Runtime, Browser, and Code Interpreter support VPC connectivity and AWS PrivateLink, so agents reach private databases and internal APIs without internet exposure ([Sept 2025 what's-new](https://aws.amazon.com/about-aws/whats-new/2025/09/amazon-bedrock-agentcore-runtime-browser-code-interpreter-vpc-privatelink-cloudformation-tagging)).
- **Identity & credentials.** [AgentCore Identity](https://aws.amazon.com/blogs/security/securing-ai-agents-with-amazon-bedrock-agentcore-identity) gives each agent a *workload identity* plus a KMS-encrypted **token vault** for OAuth tokens and API keys; user-delegated tokens are retrievable only by the specific agent acting on behalf of that user ([docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/understanding-agent-identities.html)). Federates with Cognito, Okta, and Entra ID.
- **Gateway + Policy: the governance choke point.** Gateway exposes enterprise APIs as MCP tools and authenticates both inbound agent calls and outbound tool calls. **AgentCore Policy**, [GA March 2026](https://aws.amazon.com/about-aws/whats-new/2026/03/policy-amazon-bedrock-agentcore-generally-available/), evaluates every tool invocation against Cedar policies with a **default-deny** posture and lets security teams write rules outside agent code ([AWS Security Blog on Cedar choice](https://aws.amazon.com/blogs/security/why-policy-in-amazon-bedrock-agentcore-chose-cedar-for-securing-agentic-workflows/)).
- **Audit.** Built-in tracing captures agent reasoning steps, tool invocations, and model interactions; access decisions are logged to CloudTrail ([observability overview](https://medium.com/@onkarmishra/building-secure-scalable-and-observable-agentic-systems-using-agentcore-b6ad8226f970)).

### Microsoft — ACA Dynamic Sessions + Foundry Agent Service

Microsoft splits the problem: dynamic sessions provide the raw untrusted-code sandbox (and power Copilot's own code interpreter), while Foundry Agent Service plus Entra Agent ID handle identity, network, and lifecycle governance.

- **Dynamic sessions isolation.** Each session runs in its own **Hyper-V virtualization boundary**, with prewarmed pools allocating sandboxes in milliseconds and automatic deprovisioning after cooldown ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/container-apps/sessions), [GA announcement](https://techcommunity.microsoft.com/blog/appsonazureblog/azure-container-apps-dynamic-sessions-general-availability-and-more/4303561)). Microsoft Copilot itself executes LLM-written Python in these sandboxes ([launch blog](https://techcommunity.microsoft.com/blog/appsonazureblog/new-secure-sandboxes-at-scale-with-azure-container-apps-dynamic-sessions/4142148)).
- **Foundry Agent Service governance.** Publishing an agent promotes it into a managed Azure resource with a dedicated endpoint, an independent identity, full audit trails, and registration in the Entra Agent Registry ([secure/governable agents blog](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/building-secure-governable-ai-agents-with-microsoft-foundry/4472736)).
- **Network.** End-to-end private networking — managed VNet or bring-your-own VNet — and outbound traffic restricted with Azure Firewall, NSGs, and user-defined routes so agents cannot access unapproved destinations ([network isolation deep dive](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/securely-build-and-manage-agents-in-azure-ai-foundry/4415186)).
- **Identity: Entra Agent ID.** Each agent gets a dedicated Microsoft Entra identity — a first-class non-human identity type — with scoped resource access and integration with Defender and Purview ([securing Azure AI agents](https://techcommunity.microsoft.com/blog/azuredevcommunityblog/securing-azure-ai-agents-identity-access-control-and-guardrails-in-microsoft-fou/4500242)).
- **Prompt injection framing.** [Prompt Shields](https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection) — classifier-based detection of direct jailbreaks and *indirect* injections — wired into Defender for Cloud ([MSRC on indirect prompt injection defense](https://www.microsoft.com/en-us/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks)).

### Google Cloud — gVisor Everywhere

Google's strategy standardizes on gVisor, its user-space application kernel, as the common isolation layer across serverless, Kubernetes, and the managed agent platform.

- **Cloud Run sandboxes** (public preview, 2026) are a native runtime for executing untrusted code and agent workloads, starting in milliseconds, with benchmarks of 1,000 sandboxes at ~500 ms average latency; a `sandbox` CLI lets an agent safely run sub-agents or browsers isolated from its own container ([Google Cloud blog](https://cloud.google.com/blog/topics/developers-practitioners/google-cloud-run-sandboxes-are-in-public-preview)).
- **GKE Agent Sandbox**, announced at Cloud Next '26 as an open-source Kubernetes SIG subproject, delivers gVisor kernel-level isolation at up to 300 sandboxes/second ([InfoQ](https://www.infoq.com/news/2026/05/gke-agent-sandbox-hypercluster/)). A **secure-by-default managed NetworkPolicy** blocks egress to RFC 1918 private ranges, cluster DNS, and the metadata server, while a two-tier Validating Admission Policy makes gVisor usage and network/filesystem isolation *immutable* by users ([GKE docs](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/agent-sandbox)).
- **Vertex AI Agent Engine** adds the managed-platform governance layer: [Code Execution](https://discuss.google.dev/t/introducing-code-execution-the-code-sandbox-for-your-agents-on-vertex-ai-agent-engine/264336) runs agent-generated Python in a managed sandbox; [VPC Service Controls](https://docs.cloud.google.com/vertex-ai/docs/general/vpc-service-controls) place deployed agents inside a service perimeter blocking all public internet access — a direct anti-exfiltration control; [Agent Engine Threat Detection](https://cloud.google.com/agent-builder/agent-engine/overview) watches for attacks on deployed agents.
- **Agent identity.** [Agent Identity](https://cloud.google.com/agent-builder/agent-engine/agent-identity) gives each agent a cryptographically attested SPIFFE-based identity tied to the agent's lifecycle: no long-lived keys, access tokens cryptographically bound to the agent's X.509 certificates — explicitly positioned as more secure than shared service accounts.

### Anthropic — sandbox-runtime, Claude Code Sandboxing, "How We Contain Claude"

Anthropic is the most transparent vendor about failure modes, publishing an engineering post ([May 30, 2026](https://www.anthropic.com/engineering/how-we-contain-claude)) that Simon Willison singled out for its specificity ([review](https://simonwillison.net/2026/May/30/how-we-contain-claude/)).

- **Open-source sandbox-runtime (srt).** A lightweight OS-level sandboxing tool — Seatbelt on macOS, bubblewrap on Linux — enforcing filesystem and network restrictions on arbitrary processes without a container, published as `@anthropic-ai/sandbox-runtime` so any agent builder can adopt the same primitives Claude Code uses ([GitHub](https://github.com/anthropic-experimental/sandbox-runtime), [InfoQ](https://www.infoq.com/news/2025/11/anthropic-claude-code-sandbox)).
- **Claude Code sandboxed Bash.** Confines every Bash command and its children: writes limited by default to the working directory; fine-grained `allowWrite`/`denyWrite`/`denyRead`/`allowRead` rules (narrower rules win, so a broad allow can't re-expose `~/.env`); per-domain network approval routed through a proxy. Managed settings can enforce sandboxing org-wide as a hard security gate ([sandboxing docs](https://code.claude.com/docs/en/sandboxing)).
- **Containment philosophy.** Anthropic matches isolation strength to user oversight: gVisor server-side containers for claude.ai; OS sandboxes for developer-supervised Claude Code (permission prompts fell 84% while catching ~83% of overeager behaviors — motivated by telemetry showing users approved ~93% of prompts anyway, i.e. approval fatigue); and full VMs for Cowork's non-technical users, where credentials stay in the host's keychain and never enter the guest, agents receiving only ephemeral session-scoped tokens ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)).
- **Rogue-agent framing and admitted failures.** Threats bucketed as user misuse, model misbehavior, and external attackers; environment-layer controls are primary because classifiers can't catch user-typed injections. Disclosed incidents include an allowlist bypass where a malicious workspace file exfiltrated data through Anthropic's *own* Files API on an approved domain — leading to reframing an egress allowlist "from a destination filter to a capability grant," plus a defensive in-VM MITM proxy that rejects attacker-embedded API keys ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude); [independent bypass research](https://oddguan.com/blog/second-time-same-sandbox-anthropic-claude-code-network-allowlist-bypass-data-exfiltration/)). Forward-looking risks named: memory poisoning, multi-agent trust escalation, unresolved agent-identity semantics.

### OpenAI — Codex Sandboxing and Approvals

Codex's model rests on three ideas: run work inside a sandbox, ask before anything escapes it, and keep the network closed unless opened ([Codex security](https://developers.openai.com/codex/security)).

- **OS-enforced sandbox per platform.** Seatbelt on macOS; user-namespace isolation with Landlock/seccomp on Linux and WSL2; native Windows Sandbox in PowerShell ([sandboxing docs](https://learn.chatgpt.com/docs/sandboxing)).
- **Three sandbox modes × three approval policies.** `read-only`, `workspace-write` (default), and `danger-full-access`; approval policies `untrusted`, `on-request`, `never` — a deliberate separation of *technical boundary* from *authorization gate*. Notably, `approvals_reviewer = "auto_review"` can route approval requests to a reviewer agent instead of the human — a delegated-HITL pattern ([sandboxing docs](https://learn.chatgpt.com/docs/sandboxing), [agent approvals docs](https://developers.openai.com/codex/agent-approvals-security)).
- **Network closed by default; managed egress at scale.** For internal deployment OpenAI built a managed network policy that allows expected destinations, blocks unwanted ones, and requires approval for unfamiliar domains ([Running Codex safely at OpenAI](https://openai.com/index/running-codex-safely/)). In ChatGPT Work, admins govern agent internet access via data controls.

### Docker — Docker Sandboxes and Enhanced Container Isolation

Docker's pitch targets the local-developer gap: agents are risky on the host, plain containers share the host kernel, and full VMs are too heavy for ad hoc agent work ([InfoWorld](https://www.infoworld.com/article/4177309/docker-sandboxes-and-microvms-explained.html)).

- **MicroVM sandboxes.** [Docker Sandboxes](https://www.docker.com/products/docker-sandboxes/) run coding agents (Claude Code, Codex CLI, Copilot CLI, Gemini CLI, and more) in disposable microVMs — each with its own kernel, filesystem, and private Docker daemon — full production availability January 30, 2026, on a proprietary VMM (not Firecracker) so it works on macOS and Windows ([Docker blog](https://www.docker.com/blog/docker-sandboxes-run-claude-code-and-other-coding-agents-unsupervised-but-safely/), [docs](https://docs.docker.com/ai/sandboxes/)).
- **Threat model and controls.** The trust boundary is the VM: the agent is assumed fully privileged *inside* it. Network egress is deny-by-default with allowlists; permitted outbound TCP is proxied through the host; UDP/ICMP blocked. Credentials get first-class protection: a host-side proxy injects auth headers into outbound requests so raw credential values never enter the VM. An explicit warning: agents can plant implicit-execution payloads (Git hooks, CI configs, `package.json` scripts) that later run on the host ([Sandboxes security docs](https://docs.docker.com/ai/sandboxes/security/)).
- **Enterprise governance.** Paid plans let org admins centrally enforce network, filesystem, and MCP policies across every developer's sandboxes. Researchers have shown residual risk: an attacker who can influence sandbox *configuration* can inject a Docker-socket bind mount and escape — configuration is itself part of the trust boundary ([arXiv analysis](https://arxiv.org/pdf/2512.12806)).

### NVIDIA — NeMo Guardrails, NemoClaw, OpenShell

NVIDIA plays the cross-vendor safety-tooling role, framing the risk as "a single compromised agent can expose customer data, execute unauthorized transactions, or violate compliance requirements across thousands of interactions" ([CrowdStrike/NVIDIA](https://www.crowdstrike.com/en-us/blog/secure-homegrown-ai-agents-with-crowdstrike-falcon-aidr-and-nvidia-nemo-guardrails/)).

- **NeMo Guardrails** is the open-source programmable-rails library for agentic apps, shipping with Nemotron Safety models for content safety, PII detection, jailbreak detection, and topic control; CrowdStrike Falcon AIDR integrates with it for detection-and-response telemetry over agent traffic — an emerging "EDR for agents" pattern ([CrowdStrike](https://www.crowdstrike.com/en-us/blog/secure-homegrown-ai-agents-with-crowdstrike-falcon-aidr-and-nvidia-nemo-guardrails/)).
- **NemoClaw + OpenShell.** [NemoClaw](https://www.nvidia.com/en-us/ai/nemoclaw/) is a set of open blueprints for taking autonomous agents to *governed* deployment; its **OpenShell** open-source runtime enforces policy-based security, network, privacy, and inference guardrails ([SDxCentral](https://www.sdxcentral.com/news/nvidia-details-nemoclaw-security-guardrails-in-wake-of-ai-agent-concerns/)).

### Cross-Vendor Patterns

1. **MicroVM/gVisor as table stakes.** Every hosted offering leads with hardware- or kernel-level isolation per session — Firecracker (AWS), Hyper-V (Azure), gVisor (Google, claude.ai), proprietary microVMs (Docker) — while local agent CLIs converge on OS primitives (Seatbelt, bubblewrap/Landlock/seccomp) ([comparison guide](https://northflank.com/blog/how-to-sandbox-ai-agents)).
2. **Egress is the anti-exfiltration control.** Deny-by-default networking with domain allowlists appears everywhere, but Anthropic's disclosed bypass shows the frontier: an allowlisted domain is a *capability grant*, not just a destination; defenses are moving to protocol-aware proxies ([Anthropic](https://www.anthropic.com/engineering/how-we-contain-claude)).
3. **Agents are getting first-class identities.** AWS workload identities + token vault, Entra Agent ID, and Google's SPIFFE-based Agent Identity all reject shared service accounts and long-lived keys in favor of per-agent, lifecycle-bound, auditable principals.
4. **Policy engines move governance out of agent code.** Cedar-based AgentCore Policy, GKE's immutable admission policies, Docker's org-enforced sandbox policies, and Claude Code's managed settings all let security teams constrain agents without trusting agent authors.
5. **HITL is being tiered, not removed.** Blanket approval prompts fail (Anthropic's 93%-approval telemetry); the replacement is graduated autonomy — sandboxed actions auto-approved, boundary-crossing actions gated, deny/ask rules that survive automation, and even delegated review agents (Codex `auto_review`).

### Profiles

**microsandbox** — The leading self-hosted, local-first option. Boots OCI images in libkrun microVMs in <100 ms on Linux, macOS, and Windows; SDKs for TypeScript, Python, Rust, Go; embeddable (no daemon required); detached long-running sandboxes; an MCP server and agent skills; and a notable "secrets that can't leak" feature (keys never enter the VM). Now maintained under [superradcompany](https://github.com/superradcompany/microsandbox) with daily commit velocity. Limitations: single-host focus — no fleet orchestration, no multi-tenant control plane, thin policy/audit story.

**Arrakis** — A one-person project that was ahead of its time: microVM isolation, REST API + Python SDK, GUI-in-VM for computer use, and its signature feature, **snapshot-based backtracking** for multi-step agent workflows. Effectively **abandoned since June 2025** (8 open issues, no commits in 14 months) and AGPL-licensed, which chills enterprise adoption. The backtracking idea remains largely unclaimed by successors.

**Anthropic sandbox-runtime (srt)** — Not a VM: OS-level filesystem/network restriction of arbitrary processes using native primitives (Seatbelt on macOS, bubblewrap on Linux) plus a proxy for domain-level egress filtering. It powers Claude Code's native `/sandbox` mode ([~84% fewer permission prompts](https://github.com/anthropic-experimental/sandbox-runtime)), and Anthropic's ["How we contain Claude"](https://simonwillison.net/2026/May/30/how-we-contain-claude/) post explains the philosophy. Limitations: weaker boundary than a VM (shared kernel), single-process orientation, beta APIs, no orchestration, no audit trail — it's a policy primitive, not a platform.

**E2B** — The de facto SDK/API standard for cloud code-interpreter sandboxes; Firecracker isolation, ~150 ms starts. The [infra repo](https://github.com/e2b-dev/infra) is Apache-2.0 and self-hostable, but self-hosting is a genuine infrastructure project: Terraform + a Nomad scheduling cluster, [GCP fully supported with AWS in beta](https://github.com/e2b-dev/infra/blob/main/self-host.md), and minimum quotas (~24 CPUs, 2.5 TB SSD) that price out small deployments (multiple third-party writeups peg the floor at roughly [$1,250/mo before usage](https://www.agenticwire.news/article/e2b-self-hosted-guide)). Its protocol compatibility is now a target for others (Dormice, EdgeBox).

**OpenSandbox (Alibaba)** — The biggest new entrant (Dec 2025 → ~15k stars by Aug 2026, CNCF landscape listing). The most complete OSS feature set for enterprise: multi-language SDKs (Python/TS/Java/Go/.NET), CLI + MCP server, a published sandbox lifecycle **protocol**, Docker and Kubernetes runtimes, ingress gateway + **per-sandbox egress controls**, a **credential vault** (secret injection without exposing real secrets to workloads), and pluggable gVisor/Kata/Firecracker isolation. Limitations: serious scale requires Kubernetes; weak local-first/macOS story; young project; Alibaba governance may concern some Western enterprises.

**kubernetes-sigs/agent-sandbox** — Kubernetes' official answer: a `Sandbox` CRD for stateful singleton workloads with stable identity, persistent storage, pause/resume, plus `SandboxTemplate`, `SandboxClaim`, and `SandboxWarmPool` for fleet-style management. Explicitly [only an orchestrator](https://github.com/kubernetes-sigs/agent-sandbox) — isolation is delegated to RuntimeClass (gVisor/Kata). Limitations: requires K8s expertise and cluster; no policy/guardrail layer of its own; no SDK-level agent ergonomics.

**Daytona** — A cautionary landmark: after reaching ~72k stars, Daytona [went closed-source in June 2026](https://www.agenticwire.news/article/e2b-vs-daytona), citing the risk of AI-assisted vulnerability discovery in public sandbox code. The repo is frozen at v0.190.0; self-hosting is no longer viable. This removed the largest "open-source" player from the self-hostable landscape overnight and left displaced users looking for alternatives ([Northflank's alternatives roundup](https://northflank.com/blog/top-daytona-io-alternatives-for-running-ai-code-in-secure-sandboxed-environments)).

**Dormice** — Explicitly the "SQLite of agent sandboxes": one binary, one SQLite ledger, one machine; **E2B-SDK-compatible by changing two URLs**; a novel lifecycle economics model (active → frozen → stopped → archived; a frozen 1 GiB sandbox drops to ~5 MiB RSS and wakes in ~50 ms). Limitations: self-declared "not ready for production," single-machine only, container (gVisor) rather than VM isolation.

**Framework integrations (LangChain / LlamaIndex)** — Thin and outsourced. LangChain's own [langchain-sandbox](https://github.com/langchain-ai/langchain-sandbox) is a small Pyodide/Deno WASM runner (~240 stars, quiet since Jan 2026); real isolation is delegated to third-party tools (E2B, Daytona, Azure). LlamaIndex likewise ships tool specs for [Azure Container Apps dynamic sessions](https://learn.microsoft.com/en-us/azure/container-apps/sessions-tutorial-llamaindex) and E2B. No agent framework owns a serious self-hostable sandbox — they all assume you'll buy one.

**DIY building blocks** — Firecracker, Kata, gVisor, libkrun, nsjail, and now apple/containerization are all healthy, but composing them into an agent platform (image pipeline, snapshotting, networking, API, policy) remains a months-long infrastructure project — which is exactly the gap the platforms above monetize.
